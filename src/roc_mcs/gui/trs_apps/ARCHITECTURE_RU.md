# TRS Apps — архитектура оболочки

## Назначение

`trs_apps` — контейнер для отдельных GUI-инструментов лаборатории, а не новый слой экспериментальной логики. Каждый модуль живёт в своём пакете `roc_mcs.gui.*`, а оболочка лишь создаёт экземпляр, помещает в вкладку и маршрутизирует навигацию.

```text
Start_TRS_Apps.vbs / trs_apps_app.py
                 │ bootstrap Python + src
                 ▼
          TRSAppsWindow
   ┌─────────────┼──────────────────────┐
   │             │                      │
 AppLauncherRail WindowTitleBar     workspace splitter
   │             │                   ┌───────┴───────┐
 AppSpec        split/close         AppPane A      AppPane B
   │                                 tabs           tabs
   ├── LiveRocDashboard (single instance)
   ├── RockingCurveExplorerWindow (HDF5, multi-instance)
   ├── Detector (planned placeholder)
   └── Archive (planned placeholder)
```

## Модули

| Модуль/класс | Ответственность | Не делает |
|---|---|---|
| `app_registry.py / AppSpec` | Стабильные ID, заголовок, иконка, режим единственного экземпляра и статус приложения | Не импортирует GUI-модули и не запускает оборудование |
| `app_host.py / TRSAppsWindow` | Создание приложения по запросу, вкладки, split/unsplit, закрытие страниц, общий стиль | Не реализует MCS-парсинг и физические алгоритмы |
| `app_rail.py / AppLauncherRail` | Вертикальный launcher отдельных приложений | Не переключает внутренние секции приложения |
| `workspace.py / AppPane` | Вкладки одной рабочей области, пустое состояние, сигналы закрытия/активации | Не создаёт приложения |
| `window_chrome.py / ChromeSurface, WindowTitleBar, ResizeHandle` | Тёмная пользовательская полоса окна, системные операции перемещения/resize | Не управляет рабочими приложениями |
| `live_scans/` | Стримеры, калибровка, ROC-карта и экспорт | Не управляет глобальными вкладками |
| `roi_explorer/` | Анализ ROI в HDF5 2D-сканах | Не знает о других приложениях |
| `roi_explorer_app.py` | Отдельная точка входа ROI Explorer | Не создаёт оболочку TRS Apps |

## Модель вкладок

- `Live Scans` — один экземпляр, чтобы случайно не запустить два наблюдателя на одну лабораторную сессию.
- `ROI Explorer` — несколько экземпляров, каждый связан со своим HDF5-файлом.
- Нажатие на иконку модуля открывает/активирует его в текущей области. При включении split пустая вторая область становится целевой для следующего запуска.
- Закрытие split перемещает вкладки второй области в первую без уничтожения экземпляров.
- `Детектор` и `Архив` пока показывают уведомление и не создают вкладку.

## Почему QTabWidget + QSplitter

В данном сценарии вкладка представляет целое приложение/документ, а не один инструмент. `QTabWidget` подходит для вкладок, `QSplitter` — для явно переключаемого двухпанельного просмотра. `QMainWindow` с dock widgets также умеет tabify/split, но предполагает более свободное перетаскивание панелей и сложнее для строго управляемого списка отдельных приложений. Если позднее понадобится произвольное раскладывание многих панелей, можно отдельно оценить Qt Advanced Docking System; сейчас дополнительная зависимость не оправдана.

## Следующий архитектурный шаг

Сейчас для минимального вмешательства `LiveRocDashboard` и `RockingCurveExplorerWindow` размещаются как дочерние `QMainWindow` с `Qt.Widget` flags. Они сохраняют внутренний интерфейс и алгоритмы, но могут показывать собственные menu/status bars. По мере развития следует разделить каждый модуль на:

1. `*_view.py`: reusable `QWidget` рабочей области;
2. `*_window.py`: тонкая standalone-оболочка вокруг этого виджета;
3. `*_service.py`/контроллеры: работа с данными/оборудованием без UI;
4. `app_host.py`: только интеграция в tabs/split.

Двигаться к этому стоит по одному приложению и с регрессионным сравнением результатов.

## Проверки перед работой с приборами

`TRS Apps` не управляет прессом/детектором непосредственно. В этой версии только создаются окна Live Scans/ROI Explorer; детектор и архив заглушки. Перед интеграцией нового приборного приложения отдельно проверить работу worker-thread, аварийный останов и закрытие окна. Ни один GUI-обработчик не должен блокировать event loop длительной операцией.
